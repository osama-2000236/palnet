# 14. WS-10 — Messaging: groups, requests, voice, outreach

## 14.1 What the market forces

§2.8: the advance-fee scam happens in the inbox. §2.3: voice beats text at low bandwidth and low literacy, and a 32 kbit/s Opus clip is cheaper than the photo people currently send instead. §2.2: an employer with 400 applicants cannot have 400 open threads. `ChatRoom.isGroup` and `title` are committed columns with **zero UI on either platform**.

## 14.2 Data

```prisma
enum MessageKind    { TEXT MEDIA VOICE SYSTEM }
enum RoomKind       { DIRECT GROUP HIRING INQUIRY }
enum RequestState   { PENDING ACCEPTED DECLINED }
enum OutreachState  { SENT ACCEPTED DECLINED EXPIRED }

model MessageRequest {
  id         String       @id @default(cuid())
  room       ChatRoom     @relation(fields: [roomId], references: [id], onDelete: Cascade)
  roomId     String       @unique
  requester  User         @relation("RequestRequester", fields: [requesterId], references: [id], onDelete: Cascade)
  requesterId String
  recipient  User         @relation("RequestRecipient", fields: [recipientId], references: [id], onDelete: Cascade)
  recipientId String
  state      RequestState @default(PENDING)
  createdAt  DateTime     @default(now())
  respondedAt DateTime?
  @@index([recipientId, state])
}

// Employer → candidate outreach. The InMail analogue, capped and never a
// consumer upsell (§3.4 #76).
model Outreach {
  id         String        @id @default(cuid())
  company    Company       @relation(fields: [companyId], references: [id], onDelete: Cascade)
  companyId  String
  sender     User          @relation("OutreachSender", fields: [senderId], references: [id], onDelete: Cascade)
  senderId   String
  recipient  User          @relation("OutreachRecipient", fields: [recipientId], references: [id], onDelete: Cascade)
  recipientId String
  jobId      String?
  room       ChatRoom?     @relation(fields: [roomId], references: [id], onDelete: SetNull)
  roomId     String?
  state      OutreachState @default(SENT)
  createdAt  DateTime      @default(now())
  expiresAt  DateTime
  @@unique([companyId, recipientId, jobId])
  @@index([companyId, createdAt])
  @@index([recipientId, state])
}

model AwayMessage {
  user      User      @relation(fields: [userId], references: [id], onDelete: Cascade)
  userId    String    @id
  body      String    @db.Text
  activeFrom DateTime?
  activeTo   DateTime?
  updatedAt DateTime  @updatedAt
}
```

**Changed `ChatRoom`:** `kind RoomKind @default(DIRECT)`, `jobId String?`, `inquiryId String?`. **Changed `Message`:** `kind MessageKind @default(TEXT)`, `voiceUrl String?`, `voiceSeconds Int?`, `voiceWaveform Int[]` (16 buckets, 0–100 — enough to draw a waveform without downloading the audio), `flaggedReason String?` (set by the scam scanner, §16.3).

## 14.3 Rules — decided

- **Message requests.** A first message from a non-connection, non-follower creates a `MessageRequest` and the room does not appear in the recipient's primary inbox until accepted. **The requester may send exactly one message before acceptance** — this is the single most effective anti-harassment control available and it costs nothing.
- **Outreach cap.** `EMPLOYER_PRO` gets 30 per calendar month, `EMPLOYER_BASIC` 5, `EMPLOYER_FREE` 0. Unused does not roll over. `@@unique([companyId, recipientId, jobId])` means one company cannot re-contact the same candidate about the same job. **An outreach message is never billed per-message** — it is an entitlement, so the incentive is to send fewer and better.
- **Group rooms.** Created by a hiring team (`kind = HIRING`, scoped to a `Job`), by a group's moderators, or by any member with 2–20 participants. `HANDOFF.md` records that `isGroup` has no UI; this builds it.
- **Voice.** 32 kbit/s mono Opus, **120-second ceiling** (480,000 bytes = 469 KiB). Recorded with `expo-av` on mobile and `MediaRecorder` on web. Waveform computed client-side at record time so the list can render without fetching the audio. Auto-download **never**; the play button fetches.
- **Away message** renders as a `SYSTEM` message the first time someone messages you while it is active, once per room per activation.
- **Inbox tabs:** الأساسي · الطلبات · المؤرشف. Replaces LinkedIn's Focused/Other, which sorts by an opaque model; these three are sorted by a rule the user can state.

## 14.4 API, surfaces, tests

`GET /messaging/requests` · `POST /messaging/requests/:id/respond` · `POST /messaging/rooms/:id/participants` · `DELETE /messaging/rooms/:id/participants/:userId` · `PATCH /messaging/rooms/:id` (title) · `POST /messaging/rooms/:id/messages` (changed: accepts `kind`, `voiceUrl`, `voiceSeconds`, `voiceWaveform`) · `POST /outreach` · `GET /outreach/me` · `GET /outreach/quota` · `PUT /me/away-message` · `DELETE /me/away-message`.

**Web:** `messages` gains the three tabs, `messages/requests`, `messages/[roomId]/participants`, `settings/away`. **Mobile:** the same, plus voice recording, which is the surface where mobile leads and web follows.

**New components:** `VoiceRecorder`, `VoiceBubble` (waveform + duration + play), `RequestCard`, `ParticipantList`, `OutreachComposer`, `QuotaMeter`, `AwayMessageForm`. `MessageBubble` gains a `kind` prop in **both** kits in the same commit.

**Tests:** one-message-before-acceptance; the outreach unique constraint and monthly quota reset; voice size/duration gates; waveform bucket count; that a `HIRING` room's participants are exactly the `CompanyMember`s with access plus the candidate; SSE fanout to a group room; away-message once-per-room-per-activation.

# 15. WS-11 — Low bandwidth, offline, and the Gaza path

## 15.1 What the market forces

This is the workstream that makes the rest usable. §2.3 in full: 39% of Palestinians have no internet access; 64% of Gaza's towers are offline; **Gaza's mobile data is 2G**; West Bank 4G was approved in January 2026 with a six-month stated rollout; there is no 5G spectrum; Israel retains authority over frequency allocation and equipment imports.

A 2G connection delivers roughly 20–40 kbit/s. **At 30 kbit/s, every 24 KB of payload costs 6.4 seconds.** That number is the design constraint for the entire product and it is why the budgets below are hard assertions in CI rather than aspirations in a doc.

## 15.2 The budget table — asserted in CI

`apps/api/test/payload-budget.e2e-spec.ts` fails the build if any of these is exceeded. Gzipped JSON, no media.

| Endpoint | Budget | At 30 kbit/s |
| --- | --- | --- |
| `GET /feed` (10 posts) | 24 KB | 6.4 s |
| `GET /jobs` (20 jobs) | 18 KB | 4.8 s |
| `GET /profiles/:handle` | 12 KB | 3.2 s |
| `GET /messaging/rooms` (20) | 10 KB | 2.7 s |
| `GET /messaging/rooms/:id/messages` (30) | 14 KB | 3.7 s |
| `GET /notifications` (20) | 9 KB | 2.4 s |
| `GET /search/*` (20 hits) | 12 KB | 3.2 s |

Achieving these requires three things the DTOs do not do today: **field selection** (`?fields=` with a server-side allowlist per resource), **avatar URLs without query strings**, and **no nested author object repeated per post** — the feed response carries an `authors` map keyed by id and posts reference it. That last change alone saves roughly 40% on a 10-post feed page where several posts share an author.

## 15.3 Connection-class detection and the modes

```ts
export type ConnectionClass = "offline" | "slow" | "moderate" | "fast";
```

Web: `navigator.connection.effectiveType` → `slow-2g|2g` = `slow`, `3g` = `moderate`, `4g` = `fast`; absent → `moderate`. Mobile: `@react-native-community/netinfo` `cellularGeneration` → `2g` = `slow`, `3g` = `moderate`, `4g|5g` = `fast`; wifi = `fast`.

**DECIDED — three modes, and `slow` is a default, not an option:**

| Mode | Trigger | Behaviour |
| --- | --- | --- |
| **خفيف (light)** | Automatic on `slow`; manually selectable always | No image auto-load — blurhash placeholder plus a tap-to-load with the KB cost in the label. No avatars above 32px. No video. Feed page size 5. Prefetch off. SSE degrades to a 120-second poll. |
| **عادي (normal)** | `moderate` | Images load at 640px wide, WebP. Feed page size 10. SSE on with the standard backoff. |
| **كامل (full)** | `fast` | Images at 1080px. Feed page size 10. Prefetch the next page. |

The mode is **shown in the UI, not hidden** — a persistent chip in the app chrome reading خفيف / عادي / كامل, tappable to change. A user on 2G who does not know why the product looks sparse will conclude it is broken.

**Server cooperation:** the client sends `X-Baydar-Connection: slow|moderate|fast`, and the API uses it to pick image variant URLs and default page size. It is a hint, never a security boundary, and it is never used for anything but payload shaping.

## 15.4 The outbox

**DECIDED — four actions are durable**, because losing any of them costs the user something real: publishing a post, sending a message, submitting a job application, and confirming a `WorkProof`.

```ts
interface OutboxEntry {
  id: string;                 // client-generated UUID, doubles as the idempotency key
  kind: "POST" | "MESSAGE" | "APPLICATION" | "WORK_PROOF_CONFIRM";
  payload: unknown;           // the request body
  createdAt: number;
  attempts: number;
  lastError?: string;
  state: "queued" | "sending" | "failed";
}
```

Storage: `localStorage` is forbidden in artifacts but this is the real app — web uses **IndexedDB** via a thin wrapper in `@baydar/shared/src/outbox`; mobile uses `expo-sqlite`. The queue logic, retry schedule and idempotency handling live in `@baydar/shared` and are **one implementation with two storage adapters**, which is what keeps the two platforms from diverging.

Retry: exponential backoff `2^n` seconds capped at 300, 8 attempts, then `failed` with a user-visible entry in a "لم تُرسل" tray that offers retry or discard. **Never silently drop.**

Server side: every one of the four endpoints accepts an `Idempotency-Key` header. `Message` already has `@@unique([roomId, authorId, clientMessageId])`; `Post`, `Application` and `WorkProof` gain the same pattern via a new `IdempotencyRecord` table keyed `(userId, key)` with a 48-hour TTL, storing the original response so a replay returns the same body and status rather than a conflict.

## 15.5 Offline reads

- **Web:** a service worker with a stale-while-revalidate cache for the last feed slate, the member's own profile, the last 20 message rooms with their last 30 messages each, saved jobs, and any explicitly downloaded learning path. Cache ceiling 40 MB, LRU eviction.
- **Mobile:** the same set, in `expo-sqlite`, with the same ceiling.
- **The offline banner already exists** on mobile. Web gains a twin, and both gain a "آخر تحديث" timestamp, because stale data presented as live is worse than no data.

## 15.6 Media

- Every uploaded image is stored in **three variants** — 320w, 640w, 1080w — plus the blurhash that already exists. Generated by Cloudflare Images on upload (`CLOUDFLARE_IMAGES_SCAN_URL` is already an env key; the transform endpoint is a sibling).
- **Uploads are resumable.** A 2 MB photo on 2G is nine minutes; a connection drop at minute eight currently loses everything. R2 multipart with 256 KB parts, resumed from the outbox.
- Avatars: 96w and 32w only.
- **DECIDED:** no image is ever loaded above the variant the mode allows, enforced in the `Avatar` and media components in **both** kits, not at the call sites.

## 15.7 Tests and gates

- The payload budget e2e spec, per endpoint, as a build gate.
- Outbox: replay produces one row; the shared queue's spec runs against both storage adapters (one spec, two adapters — the lockstep proof).
- Idempotency: the same key returns the identical response body and status.
- Mode switching: a fixture forcing `slow` asserts no image request is made and that page size is 5.
- Resumable upload: a simulated drop at 60% resumes and completes.
- SSE degradation: on `slow`, the client polls at 120 s and does not open an EventSource.
- **A synthetic 2G Playwright profile** (`--throttle 30kbps 400ms RTT`) runs the feed, jobs, and messages journeys and asserts first-contentful-paint under 8 seconds and interaction-ready under 12. These are not good numbers; they are the honest ones for 2G, and having them measured is the point.

# 16. WS-12 — Trust, safety and the scam economy

## 16.1 What the market forces

§2.8. In a market with 280,000 unemployed, the advance-fee job scam is not spam — it is the failure mode that makes a job platform worthless. The repo already knows: `ReportReason` carries `FEE_REQUEST`, `GHOST_JOB` and `ID_REQUEST`, which no generic social network has. §2.2: 18.6% female labour-force participation means the safety posture is also a market-size decision.

## 16.2 Employer verification

Specified in §10.4. It is repeated here because it is a safety control first and a hiring feature second: **an unverified employer's job is visible to nobody but its author.**

## 16.3 The outbound scam scanner

**DECIDED.** A rules-based scanner — not a model — runs on every outbound message from a user who is not a 1st-degree connection of the recipient, and on every job description at publish.

Three signal families, each a maintained list in `@baydar/shared/src/safety/patterns.ts` with Arabic (MSA + Levantine) and English variants:

1. **Fee request** — رسوم, تأمين, دفعة, عمولة, حوّل, تحويل بنكي, رسوم تسجيل, تأمين وظيفة, "transfer", "registration fee", "deposit", combined with a job or hiring context term.
2. **Identity harvest** — صورة الهوية, جواز السفر, رقم الحساب, بيانات البنك, "send your ID", "passport copy", "bank details".
3. **Off-platform pull** — an immediate push to WhatsApp/Telegram with no prior exchange, plus a payment or identity term in the same message.

**Actions, graduated and each specified:**

- **Match → warn the sender**, before send, with an interstitial that names the pattern and lets them send anyway. Most matches are innocent (a recruiter genuinely explaining a syndicate's registration fee).
- **Match → flag the message** (`Message.flaggedReason`) and show the recipient a non-blocking banner: «هذه الرسالة تطلب مالاً أو مستندات هوية. بيدر لا يطلب منك دفع أي مبلغ للحصول على وظيفة.» with a one-tap report that pre-fills `FEE_REQUEST` and attaches the message id.
- **Three upheld `FEE_REQUEST` reports against one account → automatic suspension** pending review (`FEE_REPORT_SUSPEND_THRESHOLD = 3`).
- **A job description matching family 1 cannot be published.** Hard block, with the matched phrase highlighted. A job posting is a broadcast; the cost of a false positive is one employer rewriting a sentence, and the cost of a false negative is measured in people's rent money.

**The scanner never reads a message between two 1st-degree connections.** That is a privacy line and it is also where the scam does not live.

## 16.4 The privacy and safety posture

**DECIDED — stricter than LinkedIn's defaults, for the reasons in §2.2 and §2.8:**

| Control | Default | Notes |
| --- | --- | --- |
| Profile photo | **Optional.** No-photo profiles render a dignified generated avatar from the member's initials over a token-derived warm tint — never a grey silhouette | A grey silhouette reads as an incomplete profile and penalises exactly the members who chose not to post a photo |
| Who can message me | Connections + verified employers | Others go to Requests (§14.3) |
| Who can see my connections | Connections only | LinkedIn defaults this open; here it is a safety surface |
| Who can see my phone | Nobody, ever | `User.phone` is never in any DTO. Asserted by a test over the whole route table |
| Profile visible to logged-out visitors | **No** | `/in/[handle]` requires a session. Only `/j/[id]` is public, and only because a shared job link must open |
| Who can see my activity | Connections + followers | |
| Restrict | Available on every profile and every message | They see me; they cannot message or comment |
| Search-engine indexing | Off, for member profiles | `robots` noindex on `/in/*`; `/j/*` and `/company/*` are indexable |

**Women-specific surfaces — DECIDED, and framed as market access rather than protection:**

- A `GENDER_SEGREGATED` flag on `Group` (for the professional women's groups that exist in this market and that women's participation genuinely depends on), with membership gated on a self-declared `Profile.addressGender = FEMININE`. Self-declared, never verified — verification here would be both impossible and offensive.
- A remote-work-first job filter, saved by default for members who opt into it.
- Report reasons gain `HARASSMENT_SEXUAL` as a distinct member of `ReportReason`, because folding it into `HARASSMENT` loses the triage priority it needs.

## 16.5 Two-sided ratings — the anti-gaming rules

`HANDOFF.md` gap #3: complete backend, zero UI, *"the only item on the list that needs a product decision before code."* **Here is the decision.**

The existing unique constraint `(raterId, rateeId, context, jobId)` supports all three standard mitigations. All three are adopted:

1. **Simultaneous blind reveal.** Neither side sees the other's rating until both have submitted, or until the 14-day window closes — whichever first. `UserRating` gains `revealedAt DateTime?`. Unrevealed ratings are invisible to everyone including moderators' default view.
2. **Minimum count before any average.** `MIN_RATINGS_FOR_AVERAGE = 4`. Below it, `EvidenceSummary.ratingAvg` is `null` and the UI shows the count only. This is what stops a single retaliatory 1-star from defining someone.
3. **A window tied to the application lifecycle.** Rating opens when an `Application` reaches `HIRED` and closes **14 days after** the associated `WorkProof` is confirmed, or 60 days after `HIRED` if no proof appears. Outside the window, `POST /ratings` returns `RATING_WINDOW_CLOSED`.

Two further rules, both derived from this market rather than from the general literature:

4. **A rating cannot be given by an unverified employer.** Otherwise a scam account rates its victims on the way out.
5. **A rating whose associated report was upheld is voided**, not hidden — `UserRating.voidedAt`, excluded from every aggregate, retained for the audit trail.

## 16.6 Moderation

The existing `/moderation` admin area gains four queues: employer verifications, professional-body licence verifications, scam-flag reviews, and appeals.

**Appeals — new and required.** A suspended account or a removed post gets one appeal, reviewed by a different moderator than the one who acted (`ModerationAction.actorId` makes this checkable), with an SLA of 72 hours shown to the appellant. `Appeal` model: `(id, subjectUserId, moderationActionId, body, state, reviewedById, reviewedAt, decision)`. Without an appeal path, an automated suspension is indistinguishable from a ban, and §16.3's automatic suspension makes appeals mandatory rather than optional.

## 16.7 Tests

Pattern-list coverage with a fixture of 40 real-shaped scam messages in Arabic and English and 40 innocent near-misses, asserting precision on the near-misses **first** — a scanner that cries wolf gets ignored, and an ignored scanner is worse than none. Job-publish hard block. Suspension threshold. Blind-reveal invisibility (asserted at the query layer, not the UI). Minimum-count nulling. Window boundaries from both sides. `User.phone` absent from every serialised response across the whole route table. Logged-out `/in/[handle]` returns 401, `/j/[id]` returns 200. Appeal reviewer-differs enforcement.

# 17. WS-13 — Search and relevance

## 17.1 What the market forces

§2.2: 280,000 people searching a thin job market need relevance, not keywords. §2.6: the right query is structural — "licensed electrician, Nablus, standing 3+" — not a bag of words. `arabic-fold.ts` already exists and is the right foundation.

Three defects to fix: `search.service.ts` **INNER JOINs `Company`**, so every company-less job (the whole point of making `Job.companyId` nullable) is invisible; `jobs.service.ts` orders by `createdAt` and `search.service.ts` by `updatedAt`, so neither has relevance; and there is no full-text index anywhere — the schema comments say a GIN/tsvector migration was planned since Sprint 5 and it never landed.

## 17.2 Postgres FTS for Arabic — decided

Postgres has no Arabic stemmer in core. **DECIDED — do not chase one.** The approach is a **folded-text `tsvector` using the `simple` configuration plus a trigram index**, which is the correct trade for this language and this corpus size:

```sql
-- Applied in a raw-SQL migration, per searchable table.
ALTER TABLE "Post" ADD COLUMN "searchVector" tsvector
  GENERATED ALWAYS AS (to_tsvector('simple', baydar_fold("body"))) STORED;
CREATE INDEX "Post_searchVector_idx" ON "Post" USING GIN ("searchVector");
CREATE INDEX "Post_body_trgm_idx" ON "Post" USING GIN (baydar_fold("body") gin_trgm_ops);
```

`baydar_fold(text)` is an `IMMUTABLE` SQL function implementing **exactly** the same normalisation as `packages/shared/src/arabic-fold.ts`: strip tashkeel and tatweel, unify أ إ آ → ا, ى → ي, ة → ه, ؤ ئ → و ي, normalise Arabic-Indic digits to ASCII, casefold Latin. **A test must assert the SQL function and the TypeScript function agree on a 200-string fixture**, because a divergence here produces results that are wrong in a way nobody notices for months.

Tables getting the pair: `Post.body`, `Profile` (`firstName || lastName || headline || about`), `Company` (`name || tagline || about`), `Job` (`title || description`), `ServiceListing` (`titleAr || description`), `Article` (`title || bodyMarkdown`), `Group` (`nameAr || about`), `Event` (`title || about`).

Ranking: `ts_rank_cd` for the lexical term, `similarity()` for fuzzy/typo tolerance, blended `0.7 * ts_rank_cd + 0.3 * similarity`.

## 17.3 Structured search

**DECIDED:** LinkedIn's boolean-string search is rejected (§3.6 #104). Nobody in this market writes `("electrician" OR "كهربائي") AND NOT "trainee"`. The replacement is faceted, structured search whose facets are the taxonomy that already exists.

`GET /search/people` facets: `occupationKey`, `familyKey`, `governorateKey`, `standingMin`, `hasLicence`, `licenceBodyKey`, `languageKey`, `universityKey`, `residenceCountry`, `originGovernorate`, `acceptingWork`, `openToWork`, `minEvidenceScore`.

`GET /search/jobs` facets: `occupationKey`, `governorateKey`, `reachability`, `locationMode`, `type`, `payBasis`, `payMin`, `currency`, `verifiedOnly`, `postedWithin`, `hasDeadline`.

`GET /search/services` facets: `occupationKey`, `governorateKey`, `remoteCapable`, `pricingModel`, `priceMax`, `standingMin`.

Plus `GET /search/groups`, `/search/events`, `/search/learning`, and a unified `GET /search?q=` returning the top 3 of each type with counts — the entry point that makes a single search box work.

**Saved searches:** `SavedSearch` model `(id, userId, kind, label, queryJson, alertEnabled, createdAt)`. `JobAlert` is folded into it — `JobAlert` is deprecated in §19.5 with a data migration, because two saved-search systems is exactly the drift this repo's gates exist to prevent.

**The INNER JOIN fix.** `search.service.ts`'s job query becomes a `LEFT JOIN` and every consumer switches to `jobSource()` in `packages/shared/src/schemas/job.ts`, which already exists precisely to decide whether a job reads as a business or a person. `HANDOFF.md` says *"Do not ship phase 5 before this"* — §20 places it in phase 5, before the individual job composer.

## 17.4 Surfaces and tests

**Web:** `search` gains six tabs and a facet rail (`flat`, sticky, collapsible on narrow). New `search/saved`. **Mobile:** `search.tsx` gains the six tabs and a `Sheet`-based facet picker — a rail does not fit at 390px, and this is a documented parity exception.

**New components:** `FacetRail` (web) / `FacetSheet` (mobile), `FacetChipRow`, `SavedSearchCard`, `SearchResultGroup`, `NoResultsState` (which suggests loosened facets by name rather than saying "no results").

**Tests:** SQL/TS folding agreement on 200 strings; a company-less job appears in `/search/jobs`; every facet independently and in three combinations; typo tolerance (`كهربائي` finds `كهربائى`); ranking stability; `EXPLAIN` asserting the GIN index is used, not a sequential scan — that assertion is what stops a future schema change from silently turning search into a table scan.

# 18. WS-14 — Notifications, digests and SMS

## 18.1 What the market forces

§2.3: 39% have no internet, so a push notification reaches a fraction of the audience. Email survives being offline. SMS reaches everyone, costs money, and annoys people if overused.

## 18.2 The channel matrix — decided

| Event | In-app | Push | Email | SMS |
| --- | --- | --- | --- | --- |
| Connection request / accepted | ✓ | ✓ | — | — |
| Post reaction / comment | ✓ | ✓ (batched) | — | — |
| Mention | ✓ | ✓ | — | — |
| Message received | ✓ | ✓ | — | — |
| Message request | ✓ | ✓ | — | — |
| **Application status changed** | ✓ | ✓ | ✓ | **✓** |
| **Interview invitation** | ✓ | ✓ | ✓ | **✓** |
| **`WorkProof` confirmation requested** | ✓ | ✓ | ✓ | **✓** |
| **Security alert (new device, password change)** | ✓ | ✓ | ✓ | **✓** |
| Job alert / saved search hit | ✓ | ✓ | ✓ (digest) | — |
| Standing advanced | ✓ | ✓ | ✓ | — |
| Newsletter issue | — | opt-in | ✓ | — |
| Weekly digest | — | — | ✓ | — |
| Promotion | — | — | — | — |

**SMS is exactly those four events and nothing else.** Adding a fifth requires an ADR. The rule exists because SMS is the only channel that cannot be muted without losing the ones that matter.

## 18.3 The weekly digest

One email, Saturday 09:00 `Asia/Hebron` (the start of the working week here — **not** Monday, and getting this wrong is the kind of detail that marks a product as foreign). Contents, in order: jobs matching your saved searches (max 5, with fit scores), `WorkProof`s awaiting your confirmation, pending message requests, connection requests, and one learning path matched to your occupation. **Skipped entirely if every section is empty** — an email that says "nothing happened" trains people to stop opening.

Rendered from the same constrained markdown as §7.4, so there is one renderer. Plain-text alternative always included, because it is a quarter of the bytes.

## 18.4 SMS provider

**OWNER-INPUT.** Options and their consequences: Jawwal/Ooredoo direct A2P (best deliverability, requires a local commercial agreement), a regional aggregator (faster to start, worse deliverability into Gaza), or Twilio (immediate, most expensive, and its Palestine routes are unreliable).

The code path is provider-agnostic: `SmsProvider` interface in `apps/api/src/modules/sms/`, one implementation per provider, chosen by `SMS_PROVIDER` env. Ships with a `LogSmsProvider` that writes to Pino so development and staging work with no credential, and `env.ts` gains `SMS_PROVIDER`, `SMS_API_KEY`, `SMS_SENDER_ID` as production-required when `SMS_PROVIDER !== "log"`.

**Cost control:** a hard cap of 5 SMS per user per day and 3 per event type per day, enforced in the service, plus a global daily ceiling env (`SMS_DAILY_CEILING`) that when hit logs an error and degrades to email — because an SMS loop bug at 0.04 USD a message is a budget incident, not a bug.

## 18.5 Grouping, digests and tests

`Notification.dedupeKey` already exists and collapses duplicate unreads. Extend with **rollups**: five reactions on one post become one notification reading «فلان و٤ آخرون تفاعلوا مع منشورك», stored as one row with a `count` column and an `actorIds` array capped at 5.

New: `Notification.count Int @default(1)`, `Notification.actorIds String[]`.

**Tests:** rollup collapse and expansion; the SMS matrix asserted exhaustively (a test enumerates every `NotificationType` and fails if a new one is added without a channel decision — this is how the matrix stays true); per-user and global SMS caps; digest skipping when empty; Saturday scheduling in `Asia/Hebron` across a DST boundary; plain-text alternative present on every email.
