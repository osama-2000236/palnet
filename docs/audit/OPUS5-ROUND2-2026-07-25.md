## P1 — the money and the silence

### R2-1 · Karama farming through the hire toggle

`updateApplicantStatus` awarded `VERIFIED_HIRE` (+200) through `karama.award`,
which has no idempotency of any kind. The surrounding guard only blocks
`HIRED → HIRED`, so an employer flipping an application
`HIRED → REJECTED → HIRED` re-entered the branch on every cycle and minted 200
points each time, up to the 5000 cap. Premium costs 500 points, so roughly
thirteen toggles is a free subscription, available to anyone who can post a job
and press a button twice.

`awardOnce` already existed for exactly this, the call site already passed
`refType: "application"` and `refId: applicationId`, and `KaramaLedger` already
carried the `(userId, reason, refType, refId)` unique that makes the
application id a one-time key. The fix is one word. What it cost was reading
`companies.service.ts`, which is what §3h asked for and round 1 skipped.

### R2-2 · The points checkout could be charged twice

`processPointsCheckout` built its idempotency key as `invoice-${invoice.id}`
from an invoice the same call had just created. A key derived from a row you
just minted is unique on every attempt, so it deduplicated nothing — and the
comment above it claimed the opposite, which is worse than no comment.

Two ways to lose 500 points: double-submit, or a retry after a client timeout.
And the second charge did not even buy anything, because `activateInvoice` sets
`currentPeriodEnd` to `now + intervalDays` rather than extending — so paying
twice in one term _shortens_ the term you already paid for.

Fixed by reordering and re-keying: refuse when the plan is already live, debit
before creating any row (a rejected redemption used to leave an `OPEN` invoice
and an `INCOMPLETE` subscription sitting on `/me/premium`), and key on the
purchase intent instead of on a fresh row. `karama.redeem` now also handles
losing the ledger unique race by returning the winner's result rather than
letting a raw `P2002` escape as a 500.

The whole POINTS rail had **zero** test coverage — twenty specs in
`billing.service.spec.ts` and not one for the only rail that moves a balance
synchronously. Four now.

### R2-3 · Web SSE never reconnected, and could not

This is the one I would fix first if only one could be fixed.

`EventSource` cannot send an `Authorization` header, so the browser
authenticates the stream with a token in the query string. That token is
**single-use** — `consumeStreamToken` stamps `consumedAt` and the guard rejects
a second use — and lives 60 seconds. `EventSource` retries by replaying the
identical URL, so its built-in retry always presents a spent token, gets a 401,
and per the SSE spec then stops retrying permanently on a non-2xx.

None of the four call sites reconnected either. `useMessagesStream` explicitly
called `close()` in `onerror` and never reopened. The two notification
consumers set a "dropped" flag and left the source to that doomed built-in
retry. The messages-badge stream in the app layout did nothing at all.

So any transient drop — a tunnel, a wifi handover, a laptop lid, a server
restart — ended realtime messaging and notification badges for the life of the
mount. The user sees a stale inbox and a stale badge with no indication
anything is wrong, until they happen to navigate. It is invisible in every
screenshot ever taken of this app, which is precisely why a screenshot matrix
is not a substitute for exercising behaviour.

Mobile was fine and is untouched: `react-native-sse` sends an `Authorization`
header, holds a normal access token, and its retry works. The single-use query
token exists purely to work around a browser limitation, which is why the bug
was web-only — and why "web and mobile stay in lockstep" did not catch it.

## P2

**R2-4 · The export told you who blocked you.** `GET /account/export` queried
`blockedUser` in both directions, so the envelope handed the user the identity
of every account that had blocked them. Every other surface — feed, search,
messaging, suggestions, notifications — hides blocks silently and
symmetrically; the export undid all of it in one line. On a professional
network where blocking is the remedy for harassment, handing the blocked party
a list of who blocked them is the failure that makes the feature pointless.
Outbound blocks only now.

This one is instructive about how it survived: `docs/api-contract.md` promises
the envelope carries "blocks", the implementation returns blocks, and the
controller spec asserts the envelope _shape_. Nobody had asserted what the
service actually reads, so the ambiguity in the word "blocks" was never
resolved by anything.

**R2-5 · The badge and the list disagreed.** `notifications.list` excludes
blocked actors; `countUnread` did not. The badge read "3" over a list of one,
and the only way to clear it was a mark-all-read that touched rows the user
could not see.

**R2-6 · Blocked users came back as suggestions.** `connections.suggestions`
excluded users the viewer has a `Connection` row with. Blocking writes
`BlockedUser` and never touches `Connection`, so a blocked _stranger_ — the
common case, since you block people you are not connected to — was suggested
straight back as "people you may know".

**R2-7 · 52 non-routes in the route table.** Detail in the commit; the short
version is that `app/` is Expo Router's filesystem route table and 52 files in
it were parts, hooks, styles and schemas. Two workarounds existed to un-claim
them: a fake `export default () => null` on 16 of them, and a
`HIDDEN_APP_TAB_ROUTES` list that rendered 52 no-op `<Tabs.Screen>` entries on
every mount. Round 1 closed the symptom and recorded the structural fix as out
of scope. Both workarounds are now deleted; `app/` is 41 files and all of them
are pages.

## P3 — recorded, deliberately not fixed

- **R2-8** `attachJobCounts` runs two `count()` queries per job and
  `listCompanyJobs` maps it over a page of up to 50 — 100 queries for one
  page. Real, but it is a perf issue on an employer surface with single-digit
  jobs per company at launch volume. Fix it with a `groupBy` when a company
  has enough jobs for anyone to notice.
- **R2-9** `POST /companies/:id/members` is `OWNER, ADMIN` but does not
  constrain `body.role`, so an ADMIN can mint an OWNER. Bounded by the fact
  that admins are already trusted with the company, and `updateMember` and
  `removeMember` are both OWNER-only with a last-owner guard.
- **R2-10** `seedPlans()` in `packages/db/prisma/seed.ts` is a hand-copied
  duplicate of `PLAN_DEFS` in `apps/api/src/modules/billing/pricing.ts`. They
  agree today. They are also pointless: `ensurePlan` upserts every plan from
  `PLAN_DEFS` on the first catalog read, so the seed's copy is overwritten
  within seconds of the API starting. Deleting it means `packages/db` would
  need to import from `apps/api`, which is backwards; the real fix is moving
  `PLAN_DEFS` into `@baydar/shared`, which is a bigger change than this
  finding justifies.
- **R2-11** `profiles.endorseSkill` assigns `awardOnce`'s return to a variable
  named `alreadyEndorsed`, then early-returns when it is **false**. The logic
  is right and the name is exactly backwards. Left because renaming it is a
  one-line change to a file I am not otherwise touching, and it is the kind of
  thing that belongs in the next PR that opens that file.
- **R2-12** `apps/mobile/app/(app)/_layout.tsx` sets the notification badge to
  `0` on any `notification.read` event, including a partial read of one item.
  It self-corrects because `markRead` publishes `notification.unread-count`
  immediately afterwards and SSE preserves order, so the badge flickers rather
  than lying. Left as a latent trap: the line is only correct because of an
  ordering guarantee it does not mention.

### `PAINTED_MIN` and the crop fractions

The constant was never the risk. A blank splash scores 1 and a launcher 902,
so anything from 3 to 100 separates them and there is no plausible device
where 8 sits on the boundary. The risk was the _failure mode_: a device where
it is wrong would skip cells in silence, which is exactly how its predecessor
(a 60KB PNG size threshold) failed on smaller AVDs. So it is now overridable
via `QA_PAINTED_MIN` and, more importantly, `warmUp` reports the paintedness it
actually measured when it gives up. A wrong constant now says so.

The 6%/96% crop fractions are left as they are, and this is a justification
rather than a deferral: they exist only to keep the ticking clock and the
gesture pill out of a frame-stability comparison. If they are wrong on another
device, the clock stays inside the slice, no two consecutive frames ever
compare equal, and `captureStable` falls through to `maxSettle` and shoots
anyway. **The failure is slow, not wrong** — a cell takes 20 seconds instead of
2 and the screenshot is still correct. That is the one class of harness
shortcut worth keeping, because every other one this repo has hit produced a
plausible-looking wrong image.

### Per-worker schemas for the e2e suite

Not built, deliberately. The stated problem — "e2e reports 33 failures that are
not real" — is already solved: `workers: 1` is in the config with a comment
explaining why, and the suite is 51/51 green. What remains is a _speed_
complaint about a 3.5-minute suite.

Giving each worker its own Postgres schema means provisioning and migrating N
schemas per run, threading a per-worker `DATABASE_URL` through `webServer`
(which starts one API process for the whole run, not one per worker), and
tearing them down reliably on Windows and in CI. That is a meaningful piece of
infrastructure to save two minutes on a suite that runs on push, and it adds a
new silent-failure surface — a worker pointed at the wrong schema tests the
wrong data — to a repo whose recurring theme is silent failures in test
infrastructure.

Revisit when the suite is long enough that someone skips it. At 3.5 minutes,
nobody is skipping it.

## R2-13 · The nav's active-tab underline was 17px off, on every screen

Follow-up to the previous section's open question. The `error` and `offline`
snapshots came out byte-identical and I recorded that I could not tell whether
the app distinguished the two, because `ConnectivityBanner` lives in the masked
header. It does distinguish them. The test did not.

`route.abort("internetdisconnected")` fails _requests_. It does not change
`navigator.onLine` and does not fire the `offline` event, which is the only
thing `useOnline` listens for — so an abort-based "offline" state never renders
the banner and is the error case wearing a different label. That is why the two
images matched. `ux-sad-path.spec.ts` had already been testing real offline
correctly, with `context().setOffline(true)`, the whole time.

Two changes fell out. The redundant snapshot and its `goOffline` helper are
deleted — offline is covered, correctly, one file over. And
`shots.mjs --state=offline` now uses `context.setOffline(true)` applied _after_
navigation, because a page that is offline before `goto` cannot load its own
HTML, and mid-session connectivity loss is the state a user is actually in.

Photographing the real offline state immediately turned up a defect that had
nothing to do with connectivity:

**The nav strip overflows the header, and the active-tab indicator lands below
it.** `NavButton` sizes to its own content — icon, 11px label, `py-2` — which
is 89px at 390px, inside an `h-14` (56px) header. Flex items do not shrink
below content height, so the nav overflowed 17px in each direction and the
`-mb-px border-b-2` active indicator, whose entire purpose is to sit _on_ the
header's bottom border, painted 17px below it. Measured: 17px at 390px, 4px at
1440px, on every authenticated screen.

It was invisible for the same reason everything else on this branch was
invisible — the stray olive line lands on page background of the same colour.
The offline banner has a tinted background, so the line finally showed up,
struck straight through the Arabic text.

Fix is `h-full min-h-0` on the nav and on the button, with `py-2` dropped and
`justify-center` added, so the strip is exactly header height. Underline offset
is now -1px, which is what `-mb-px` was always asking for. Hit target 55px,
comfortably over the 40px web minimum. `AppShellProfileMenu` carries the same
`-mb-px border-b-2` pattern and was measured at 0px offset — it was already
correct, so it is untouched.

The general lesson is the one this branch keeps relearning: a state nobody
captures hides defects that are not about that state. This one had been
shipping on every screen since the header was built.

## Self-review of this branch

Reviewed the whole diff before calling it done. Five findings against my own
work; four fixed, one recorded unresolved.

**🔴 The SSE fix captured a token that expires before most outages do.**
`openStream(scope, accessToken, handlers)` took the access token as an
argument, and the layout resolves one exactly once on mount and never again.
Access tokens live 15 minutes. So the first reconnect after 15 minutes minted
its stream token with a stale credential, got a 401, called `onFailed`, and
stopped the retry loop for good — the same dead stream the function exists to
prevent, just moved behind a longer fuse. A closed laptop is the canonical
case, and it is the exact example I used in the commit message. Now resolved
per attempt via `getValidAccessToken()`; the parameter is gone.

**🟡 I fixed a two-copy drift bug by making it four copies.** The badge and the
list disagreed about blocked actors because the unread predicate lived in two
places. My fix added the exclusion to `countUnread`, to `markRead`'s recount
and to `dismiss`'s recount — three more literal copies of a filter that has to
stay in sync, in the same file whose bug was caused by exactly that. One
private `unreadWhere(viewerId)`.

**🟡 `findFirstOrThrow` could turn a handled race into a 500 on the money
path.** P2002 proves the winner's INSERT happened, not that it committed, so
the loser's read can legitimately come back empty. `findFirst` with a fallback
to the live balance; the debit is still never repeated, which is the invariant
that matters.

**🔵 The day-scoped redemption key has a load-bearing, undocumented
dependency.** It is safe only because nothing in this codebase transitions a
subscription out of `ACTIVE` — verified, there are exactly two
`subscription.update` calls and neither does. If that changes, a same-day
cancel-and-rebuy replays the ledger row and grants a term without debiting.
Now named in the comment instead of implied.

**Unresolved: `a11y authed: premium (ar-PS)` is intermittent.** It failed in
two full local runs and passed in two others, passes alone, and passed 8/8
under `--repeat-each=4`. I never captured the violation text, so I am not going
to guess at a cause or claim a fix. CI has passed it on every push. Recorded
because an intermittent accessibility failure is worth someone catching the
message next time it fires, and because pretending it did not happen is how it
stays intermittent.

Also dropped the three state pixel-snapshots entirely. They failed three times
for three different reasons — a per-run fixture username, a missing Linux
baseline, then the profile-completion meter moving because an earlier spec had
edited the fixture user — and each fix masked one more region. That is the
instrument being wrong: a pixel snapshot of a page rendering live data cannot
be stable. Replaced with content assertions on the title and recovery copy,
which is what they were actually for, and which need no per-platform baselines.
`shots.mjs --state=` still sweeps every route for a human. The widening that
mattered — 7 routes to 23, plus overflow as a CI gate — is untouched.
