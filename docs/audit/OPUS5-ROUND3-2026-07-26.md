## Corrections to the design brief

The prompt asked that a ledger citation which does not hold be treated as a
finding. Two do not.

### A1.2 overstates its own severity, and names a component that renders nowhere

The brief's headline is: _"**The native app shell does not re-theme in dark mode
at all.**"_ It cites `packages/ui-native/src/AppShell.tsx:200`.

Three things are wrong with that.

1. **`ui-native`'s `AppShell` is imported by nothing.** The only match for it
   across `apps/mobile/src` and `apps/mobile/app` is the word "AppShell" in a
   comment at the top of `app/(app)/_layout.tsx`. The real mobile chrome is that
   layout plus `@/screens/tabs/TabParts`. So the file the claim is measured on is
   not on screen for any user.
2. **Only 9 of the 14 listed files freeze a colour at module scope, not 14.**
   The brief lists every file containing `StyleSheet.create`. Restricting the
   grep to `nativeTokens.color.*` _inside_ the `StyleSheet.create` block gives
   `AppHeader` (2), `AppShell` (7), `ComposerEntry` (5), `EmptyState` (2),
   `RecordCard` (3), `SearchField` (4), `Sheet` (5), `StateMessage` (2),
   `Toast` (1) — 31 refs in 9 files. The other five put only spacing and type in
   `StyleSheet.create`, which is correct and should not be changed.
   `SegmentedControl` is the pattern to copy: layout and type in the static
   sheet, every colour resolved at render from `useThemeTokens()`.
3. **Dark mode works.** All 38 mobile screens were captured in the dark theme
   this session (mean frame luminance 36 vs 246 in light) and re-theme correctly
   — surfaces, ink, olive brand, terracotta accent, chips, form controls, tab
   bar. See the evidence note below for why nobody could previously see this.

**Revised finding.** A1.2 is real but it is a latent maintenance hazard, not a
shipped visual defect: 31 colour values frozen to the light palette in 9
components, currently masked either because the component is unmounted or
because an inline `useThemeTokens` style later in the style array overrides
them. It should drop from P1 to P3. The fix is still worth doing — a frozen
colour that happens to be overridden today breaks the first time someone
reorders a style array — but it does not block anything.

### The mobile console capture cannot find what it was built to find

PR #94 added per-screen `adb logcat` capture to `apps/mobile/e2e/shots.mjs`,
modelled on the web harness whose equivalent found two missing `messaging.*`
message keys. The prompt notes it had never been exercised. It has now.

It filters logcat for the `ReactNativeJS` tag. **That tag does not exist in the
buffer on this stack** (RN 0.81 + Hermes, Expo dev client) — `adb logcat -d -v
tag` across a full 38-screen run lists no `ReactNativeJS` lines at all. JS
`console.*` is forwarded to the Metro terminal instead, where it is plainly
visible (`DEBUG [observability] Sentry disabled…`).

So every `_console__*.json` this harness has ever written is `{}`, and reads as
"38 screens, no warnings" when it means "nothing was looked at".

Not fixed properly — reading Metro's stream requires the harness to own the
Metro process, which it does not. Fixed to the extent that matters: an empty
capture across a whole cell now prints a loud warning naming the cause, so the
file can no longer be mistaken for a clean bill of health.

## The mobile matrix — 38 screens, both themes

Owed since round 2, which deferred it because bundling against a Metro instance

### Environment findings, all of which cost time

- **Ports 8081 and 4000 were both held by other worktrees** (`blissful-austin-7e6f55`'s
  Metro, `ponytail-ultra-cd7926`'s API). `shots.mjs` now takes `QA_METRO_PORT` /
  `QA_API_PORT`, because the device asks for `:8081` and `:4000`
  unconditionally and `adb reverse` is what decides which host process answers.
- **`adb reverse` does not save you from the dev client.** It rewrites
  `localhost` on the device; the Expo dev client had remembered `10.0.2.2:8081`,
  the emulator's host-loopback alias, which bypasses `adb reverse` entirely and
  went straight to the neighbouring worktree's Metro — which was itself broken
  (`Cannot find module 'dotenv'`, serving HTTP 500 to every bundle request).
  Passing a `?url=` deep link did not move it. Freeing 8081 was the only route.
- The API base _does_ honour `adb reverse`: `apps/mobile/src/lib/api.ts` defaults
  to `http://localhost:4000/api/v1`, and `localhost` on the device is the device.

### The dark cell was never capturable

`.maestro/set-appearance.yaml` declared `env: THEME: light`. Maestro 2.5.0 gives
an in-file `env` block precedence over `-e`, so every invocation tapped
`appearance-light` no matter what the harness asked for — and the flow's own
assertion passed, because light genuinely was selected. The first run produced
38 light screenshots named `…__dark.png`.

Found by cropping `settings-appearance__ar-PS__dark.png` and seeing فاتح still
selected. Fixed by deleting the defaults; verified by luminance, 246 → 36.

Guarded three ways so it cannot recur silently: a luminance assertion in
`shots.mjs` that refuses to photograph a cell whose theme does not match its
label (confirmed to fire by forcing the threshold), a `selected: true` assertion
in the Maestro flow, and the empty-console warning above.
